# 决策记录 006 —— 重排走 API（OpenAI 兼容 reranks），模型定 qwen3-rerank（2026-11-16）

- **日期**：2026-11-16
- **触发**：用户裁决「重排选 **B 走 DashScope 原生 rerank API**」。落地取证后，实际形态比选项描述更省（见第二节更正 1），**同一个 key、OpenAI 兼容接口，不需要供应商专用客户端**。
- **决定**：
  1. 重排后端 = `RERANK_BACKEND=api`，端点 `POST {RERANK_BASE_URL}/compatible-api/v1/reranks`；
  2. 模型定稿 **`qwen3-rerank`**（单文档 4,000 token）；`qwen3.7-text-rerank`（单文档 30,000 token、201 语种）列为可切换档；**`gte-rerank-v2` 禁用**（官方标注 2026-05-30 下线，今日已过期）；
  3. `RERANK_ENABLED=1` 默认开启，但**一次请求失败必须显式回退为「不重排」并打印一行说明**，禁止「界面显示开启、实际空转」；
  4. **重排分永不参与拒答阈值判定**（本记录把它从经验纪律升级为官方数学性质约束，见第三节第 1 条）。
- **性质**：可替换点变更（「重排模型」一行）。接口路径、`search(问题, 条数) -> list[Hit]`、五条不变契约、前端组件全部不动。

## 二、两条必须更正的记录（写下来，免得后人再踩）

1. **更正 005 第七节末尾我口头给出的判断**：上一轮我说「OpenAI 兼容层没有 rerank，重排要写供应商专用客户端，005 的『供应商不绑定』对它不成立」。**该结论错误**，原因是我只试了 `compatible-mode/v1/rerank`（404）就下判断。真实情况是兼容层的重排在**另一组前缀**下：`compatible-api/v1/reranks`（401 = 存在、待鉴权）。
   → 纪律教训：**探测失败只能证明「我试的那个路径不存在」，不能证明「该能力不存在」**；下否定结论前要么查文档、要么穷举命名变体。本轮已用 5 个组合补齐。
   → 连带影响：`retrieval/rerank.py` 可以复用与 `ApiEmbedder` 同一套 httpx 客户端与错误处理，**不需要专有 SDK**；但 **base_url 前缀不可从 `LLM_BASE_URL` / `EMBEDDING_BASE_URL` 推导**（`compatible-mode` vs `compatible-api`），必须独立配置 `RERANK_BASE_URL`。
2. **模型名不得沿用 `gte-rerank-v2`**：官方标注 2026-05-30 下线并推荐迁移；且它不支持兼容层。定稿 `qwen3-rerank` 后，若检索串将来超 4,000 token 再切 `qwen3.7-text-rerank`。

## 三、对本计划的四条硬约束（逐条落点）

1. **「不可跨请求比较」直接封死了把重排分当证据分的可能**。拒答阈值是在跨题目、跨召回集合上标定的量，必须使用可跨请求比较的那把尺子（`Hit.score`，来自稠密/融合）。原计划「最高重排分低于阈值」的表述已在上一轮改为「最高综合分」，本记录把它升级为**官方数学性质约束**，并在 [阶段二步骤 4b](../../plan.md) 引此条为据（此前只引参考实现的经验）。
2. **三把尺子的展示纪律**：`Hit` 现在确实存在三种量纲（综合分 0–1 相似度、BM25 词频分、relevance_score 相对分）。出处卡与证据面板**禁止把不同尺子渲染在同一列**——参考实现 §5.23 实测过「两种尺子混一列」导致「相关文件和不相关文件得分差不多」，§5.32 更出现过「面板显示 0% 却被引用」。落点：前端 `SourceCard` 的相关性标签必须注明尺子名，或只展示综合分一档。
3. **客户端必须预检长度，不许让服务端截断或静默失败**：单文档超 4,000 token 官方**返回 400 且不截断**。本项目检索串（卡片名 + 谓词 + 取值 + 引文，引文 25–160 字）远低于该值，但 [阶段二步骤 3c](../../plan.md) 的「同卡片多条目合并成块」实验若放宽块大小就会撞上。要求：`RerankClient` 发送前按 `EMBEDDING_*` 同一分词近似预算做长度预检，超限**显式报错并跳过重排**（不发送、不假装成功）。同理遵守 005 的响应完整性纪律：**返回条数 == 请求条数**，缺条目即报错，不得用默认分补齐。
4. **失败回退是默认行为，不是异常路径**：`reranks` 超时/限流/4xx → 记录一行 `[重排未生效: <原因>]`，按 RRF 融合顺序返回最终 k 条，问答链路继续。**这条同时强化「付费云服务不是唯一路径」的合规前提**（005 第四节三级降级之外，新增一档「重排缺失」降级）。

## 四、配置与代码缺口（实现落在阶段二）

`backend/.env.example` 现状仅 8 键（`LLM_*` 4、`RETRIEVAL_BACKEND`、`RAGFLOW_*` 2、`DATA_DIR`），且 005 第二节的 6 个 `EMBEDDING_*` **尚未落地**。本记录追加 4 项：

```
RERANK_BACKEND=api          # api / local_lexical / off
RERANK_BASE_URL=https://dashscope.aliyuncs.com/compatible-api/v1
RERANK_API_KEY=             # 与 LLM/EMBEDDING 可同值（同一家 key），字段仍分开，便于降级演练单独关闭
RERANK_MODEL=qwen3-rerank
RERANK_TIMEOUT_S=15
RERANK_MAX_DOCS=60          # 官方上限 500，本项目召回 30+30 去重后远小于它，设上限防手滑
```

代码面新增 `backend/app/retrieval/rerank.py`：`Reranker`(Protocol) + `ApiReranker` / `LocalLexicalReranker` / `NoopReranker` 三实现，与 `embedding.py`（005）、`extract.py`（002）同形态：**可注入、显式报错、不自动切换后端**。`Hit` 增字段 `rerank_score`（可空），已在 4b 规定不参与判定。

## 五、对阶段指标的影响

- **延迟预算**：每次问答多 1 次 HTTP 往返（本机实测同域 RTT 量级 620–700 ms 含 TLS，未含真实推理）。阶段八「在线生成 P95 ≤8 秒」的预算需给重排留出这 1 次调用；实测超预算时首选关掉重排（`RERANK_ENABLED=0`）而不是砍检索候选。
- **成本**：每次问答 1 次 rerank 请求（≤60 文档、每文档几十至几百 token），计入阶段九步骤 3b 的成本单列三类之外，**新增第四类：重排调用数与 token**。
- **命中率**：外部实测提示「小语料上重排常无收益」（Hit@1 不变，Hit@3 +3.7pt），所以**重排收益必须在阶段二步骤 6b 用我们自己的开发集量出来**，量不出收益就按 `off` 交付并写进评测报告，不得凭"业界常规"保留。

## 八、追加更正（2026-11-16，依决策记录 007 的带 key 实测）

本节成文时端点路径已由 401 探测确认存在，但**模型名有效性与全部数字口径均只有官方文档为据**。同日用户给 key 后实测，按纪律保留原文、在此更正：

| 本记录原口径 | 实测结果 |
|---|---|
| 第 1.2 节规格表「单文档最大 **4,000** token（`qwen3-rerank`）」 | 该部署服务端实际边界为 **32,768 token**：4 万汉字明确 400 并回显 `This model's maximum context length is 32768 tokens`，1.2 万汉字 200。**官方数字与部署不符**，客户端预检线取 **30,000** 留余量 |
| 硬约束 3「超限返回 400 而**非静默截断**」 | **成立**（实测报错文本精确给出 token 数）。该约束原样保留，只是数字换成实测值 |
| 第 1.2 节「单次请求 ≤500 文档」 | **证实**：501 条 400 回显 `batch size of documents … not be empty or larger than 500`。`RERANK_MAX_DOCS=60` 远低于该线，无需改动 |
| 第六节未决项「模型名 `qwen3-rerank` 是否有效」 | 有效，排序符合直觉（0.851 / 0.322 / 0.224，命中"图书馆几点开门→开放时间那条"） |
| 第七节「回滚 `off` / `local_lexical`」（未涉端点回滚） | **补一条已验证的回滚**：DashScope 原生 rerank 端点与兼容层对同一请求返回的 `relevance_score` **逐位相同**（0.8509820284844418 等三条完全一致），说明两前端背后同一服务，兼容层下线时切原生端点不改变分数语义 |

两个模型名的选择据实测定：**`qwen3-rerank` 与 `qwen3.7-text-rerank` 都可用**，定稿取 `qwen3-rerank`。理由不是质量结论（本轮无标注集，不得下此判断），只是分布形态：`qwen3-rerank` 落在 0.22–0.85 的平缓区间，`qwen3.7-text-rerank` 压成 0.042 / 0.084 / 0.965 的近二值分布。两者**分数不可互换**，换即属尺子变更；依硬约束 1（`rerank_score` 永不参与闸门判定），换它不影响拒答阈值，但会影响排序展示与阶段九 ④ 类成本口径，须在决策记录留痕。

**未决项状态**：1（单价）仍未决 → 移交 007 未决项 1；2（业务空间专属域名下 `compatible-api/v1/reranks` 是否可用）仍未测，需 WorkspaceId；3（分数与综合分是否同向）待阶段二步骤 6b；**4（检索串合并成块是否撞 4,000 上限）本项按实测关闭**——上限实为 32,768，阶段二步骤 3c 的合并档上限 512 token 远在其内，真正需要盯的是「同批一条超长拖垮整批」那类问题（发生在 embed 侧，见 007 三-3）；5（关重排后 Hit@8 是否仍 ≥85%）不变。

硬约束 1（`relevance_score` 不参与闸门）本轮**未做跨请求漂移的重复验证**：官方已明示该性质，且约束的作用域已被限制在「单次请求内排序」，再验不改变结论，故不列未决项——避免用重复探测冒充证据。
