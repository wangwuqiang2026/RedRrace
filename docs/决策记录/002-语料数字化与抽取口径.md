## 二、决定（条文）

### D02-1　`publish_date` 载体分支

> **本轮纠正（2026-11-13，D3）**：原条文把下面三者统称「年份」，并写了一个与现行代码不符的四位年区间和判据正则，还明确拒绝带月日的写法——**错在文档，代码与测试一律不动**（现行区间由终审缺陷 A 授权并有单测锁定）。下文按实现重写，**三个口径各自管各自的字段**，不得混用一个词。

**口径 1：出版年**——`registry.py` 校验登记表 `publish_date`（判据常量 `registry.py:59-60`：`_YEAR_MIN = 1840`、`_YEAR_MAX = 2100`）
- 合法区间 **1840–2100**（终审缺陷 A 明确授权，并有 `backend/tests/test_registry.py` 锁定，属现行行为）。
- **电子书**：必须是四位年份数字，**允许带月日的写法**（如 `1985年10月`、`1985-10`），只要其中的年份落在 1840–2100。
- 仍**不接受**区间（`1985—1987`）、不接受「约 1985」这类推测性表述；确需表达不确定，把说明写进 `license_note`，字段本身保持规范写法。
- 空白一律拒绝；唯一允许的占位字面值是 `年代不详`（见本节末「载体分支」）。

**口径 2：事件年**——`normalize.py` 的 `normalize_time`（判据常量 `normalize.py:31-32`：`EVENT_YEAR_MIN = 1`、`EVENT_YEAR_MAX = 2100`，校验点 `normalize.py:132`）
- 合法区间 **1–2100**，超出判 `unknown`。
- 只认两类写法：**3–4 位数字 + 「年」**（可带月日），或**四位裸数字**（如 `1522`）。
- 实测行为（`task-F1A-report.md` §6）：`1522→year`、`960年→year`、`1522年9月→month`、`2101→unknown`、`嘉靖年间→unknown`。
- **`20年`（时长歧义）与裸写 `960`（可能是页码、卷数）判 `unknown`：这是刻意的严格，不是缺陷**——取值不确定时宁可不给时间，也不让检索与冲突判定拿一个猜出来的年份。

**口径 3：年号纪年**（嘉靖年间、光绪二十年 等）
- **本轮不换算，一律保持 `unknown`，绝不猜**。换算需要年号—公历对照表与「在位第 N 年」的起算规则，属新增知识来源，未核验前不引入。
- 写成**已知限制**：涉及明代及以前的事件，时间轴会落在「年代待考」区（`docs/设计规范.md` §5.3），而不是主时间轴上；该限制的量化影响与是否补做换算，**归阶段九评测口径**（`docs/评测报告.md`，阶段九），届时按真实语料统计「因年号纪年落入待考」的条目数再定。

**载体分支（保持不变的部分）**
- **文章**：填 `YYYY-MM-DD`；确实考不出时**只允许字面值 `年代不详`**（plan 步骤 4 已定），不接受空白或其他占位串。
- 三个口径的关系：`publish_date` 只走口径 1（出版年），事实条目的事件时间只走口径 2 与 3（事件年、年号纪年）；**一个字段只有一个判据来源**，代码里由不同模块负责，测试也分开锁。
- 责任：口径 1 由 `registry.py` 校验（不合格整行拒绝入库），口径 2 与 3 由 `normalize.py` 判定（超出区间或写法不受限即 `unknown`，不抛错、不猜值）。

### D02-2　白名单判定只看两件事：机构名 + `verified`

- `domain` 与 `sections` **不参与准入判定**：`domain` 可为空字符串（6 家出版社即如此），`sections` 可为空列表，都不影响放行；引用时若要落到具体栏目，由采集人人工确认。
- 放行集合的构造：取 `verified is true` 的条目，用 `name` 与 `aliases` 归一后的字符串集合做**精确匹配**（归一 = Unicode NFKC + 去空白；不做模糊匹配、不做子串包含）。
- `verified: false` 的条目一律视为**不在名单内**，拒绝并抛含 `whitelist` 的 `ValueError`。

### D02-3　不设 `type` 分组字段（YAGNI）

白名单里机构与出版社共用一个列表，比对键由登记表的 `media_type` 决定：`电子书 → 出版社名`，`文章 → 发布机构名`。**不加** `type` 字段。只有当真出现「同一机构既出书又发文章且核验状态不同」的需求时才复议，届时先改测试再改结构。

### D02-4　人民出版社保持 `verified: true`，附「证据强度中等」注记

- 依据是中央党史和文献研究院官网的书目页 + 来源署名「人民出版社」微信公众号，**正文未出现「由人民出版社出版」字样**；该局限已写进白名单 `note`。
- 采编规则：以人民出版社为出版社的电子书**可以入库**，但答辩被追问时要能一句话说清凭哪一页核的（`verify_source` 里的 URL 直接给评委看）。
- 降级路径（保留、不启用）：若要求正文级/CIP/ISBN 证据，改回 `verified: false` 并同步撤回依赖它的登记行。

### D02-5　冲突卡片的排列顺序恒为 `source_id` 升序

- 冲突组内两条（或多条）来源的展示顺序**只按 `source_id` 升序**，与相关度分数、来源层级（核心/补充）、机构权威度**一律无关**。
- 理由：任何按可信度排序都等于系统在「隐性取舍」，违反全局约束 4「冲突不取舍」。顺序中性，读者自己判断。
- 判据：`conflict.values` 排序后 `source_id` 单调递增；测试须断言「把两条的可信度分数对调，展示顺序不变」。

### D02-6　拒答分两类原因，UI 是「说明」不是「报错」

| 原因码 | 语义 | 触发 |
|---|---|---|
| `not_covered` | 未收录：库里没有这个主体的任何条目 | 检索结果为空、或最高重排分低于拒答阈值（阶段二标定） |
| `no_evidence` | 无证据：主体在库内，但本次结论无逐字引文支撑 | 引用校验后保留句为空 |

- 答复文本必须含「当前知识库未收录」这类说明口径，并可给最近邻参考卡（参考项同样带出处，不回答未收录主体的任何事实）。

- **原「遗留的不一致」已于 2026-11-13 由 lead 同步 `plan.md`，遗留清零**：plan 阶段三示例断言四处改毕（`:595`/`:620`/`:699` 的 `body["refused"]` → `body["refusal"]`，`:621` 的 `not_in_corpus` → `not_covered`），本岗 grep 复查 `refused|not_in_corpus` 在 `plan.md` 命中 **0**；字段名与取值的唯一出处仍是 `backend/app/qa/schemas.py:103`（`refusal: bool`）与 `:112`（`refusal_reason: Literal["not_covered", "no_evidence"] | None`）。收口记录见 `docs/决策记录/000-语料来源与白名单.md` 未决项 #12。**教训留档：plan 的示例代码不是契约，写测试前必须回读 `schemas.py`。**
- **视觉**：拒答区用深蓝灰 `--refusal-ink`（`#33526B`）+ 中性纸面底 `--paper-muted`，**禁止使用错误红** `--error-red`（`#A02020` 只留给接口失败等技术故障）、禁止报错图标与「失败/错误」措辞（设计规范 R3）。语义状态仍须**颜色 + 图标 + 文字**三者齐备（R4），存疑态另用 `--disputed`。

### D02-7　生成调用超时：在线 15 s，本地 30 s

- 在线接口（`LLM_BACKEND=online`）单次调用超时 **15 秒**；本地 GGUF（`LLM_BACKEND=local`）**30 秒**。
- 超时后的行为统一：记一条 `no_evidence` 或技术故障日志（区分二者，见 D02-6 的红色只属于后者），**不得静默改写成答案**；有降级路径时按 plan「技术选型与可替换约定」退回基线。
- 两个数值进 `.env.example` 的配置项或 `core/config.py` 默认值，不硬编码在流水线里。

### D02-8　抽取流程三段式与重试

1. **大模型抽取**：提示词硬约束「只抽原文出现的事实，每条附**逐字引文**」，温度 0，提示词版本号写进问答日志（`qa/prompt.py`）。
2. **结构校验**：卡片类型 ∈ {person, event, place, time, relation}；每条事实条目必须有主体、谓词、取值、引文、定位。
3. **规则兜底**：缺引文／引文在解析原文（归一化后）找不到／谓词不在受控词表 → **丢弃该条**（不猜、不改写、不补全）。
4. 抽取失败**重试两次**后转**人工补录**，质量情况记入评测报告。

判据必须可测：第 2、3 段不依赖大模型，用固定输入即可回归（见第四节边界表）。

### D02-9　受控谓词表（至少 8 个）

`生卒年、籍贯、职务、参与事件、事件时间、事件地点、事件结果、人物关系`。

- 「至少」意味着**可增不可减**；新增谓词须同批更新归一模块的取值规则与冲突判定的谓词映射，并在测试的受控词表常量里同步。
- 表外谓词的抽取结果一律丢弃（D02-8 第 3 段）。

### D02-10　人工校对 10% 双人核对

- 抽样：随机抽 **10%** 卡片，**双人**核对（本人 + 一名同学）。
- 核对项恰好三项：① 事实是否在原文；② 引文是否**逐字**一致；③ 时间是否归一正确。
- 错误率 **>5%** → 回到提示词调整并**全量重跑**（plan 阶段一步骤 8）。
- 校对记录存 `backend/data/校对记录.csv`，**不进版本库、不入语料库**（不污染卡片表）。

### D02-11　无 API key 时的可跑路径（本条决定阶段一步骤 7 的验收边界）

**事实**：本会话无可用在线大模型密钥（`.env` 不存在、`LLM_API_KEY` 等环境变量为空、`.env.example` 只有空占位）。**实现现状（2026-11-13 12:5x 只读取证，本条已由「待实现」变为「已实现」）**：`backend/app/ingestion/extract.py` 已存在，且第 1–3 点都落地了——`extract.py:92` 定义 `class Extractor(Protocol)`（后端可注入），`:98` `class StubExtractor`（固定桩件），`:122` `class LlmExtractor`（在线后端），无 key 时 `:145-146` 显式报错要求「复制 `.env.example` 为 `.env` 并填三项，**无 key 环境下请显式改用 `StubExtractor`，抽取后端不会自动切换**」——正是本条第 1、3 点要的形态。受控谓词表见 `extract.py:34 VALID_PREDICATES`（第 9 条），重试两次转人工补录见 `extract.py:11/45` 且落 `data/待人工补录.csv`。因此本条下面的四点由「要求」转为「已被实现满足、须保持不退回」：

1. **抽取模块必须支持注入一个可替换的抽取后端**——即 `extract_cards(解析结果)` 所依赖的调用方由外部传入（接口形态类似 `qa/llm.py` 的双实现切换），而不是在模块内部写死某个 HTTP 调用。
2. **测试用固定桩件**（stub）：桩件返回**预先写死的抽取结果**，用于验证第 2 段结构校验与第 3 段规则兜底的行为——包括「缺引文丢弃」「引文不在原文丢弃」「谓词不在受控词表丢弃」「重试两次后转人工补录」这四条判据。
3. **真跑等用户补 key**：补 `LLM_BACKEND` / `LLM_BASE_URL` / `LLM_API_KEY` / `LLM_MODEL` 后即可切换到在线后端；本地 GGUF 路线同理（`local` 后端与模型路径）。
4. **这条不影响可验证性**：结构校验、规则兜底、逐字引文定位（引文能否在解析原文命中）三项**与是否有 key 完全无关**，必须有真测试；凡涉及「抽取质量本身」的指标（抽取准确率、条目产出密度）**在拿到 key 之前不得宣布达标**，评测报告里留空并写明原因。

| 提示词模板与版本号常量 | 是 | 静态断言（模板含「逐字引文」硬约束、版本号写入日志字段） | 否 |
| 抽取后端可注入（接口形态） | 是 | 注入桩件后跑通全链路，断言调用方是被注入对象 | 否 |
| 结构校验（卡片类型、条目字段齐备） | 是 | 桩件返回畸形结果 → 必须报错/丢弃 | 否 |
| 规则兜底：缺引文丢弃 | 是 | 桩件缺 `quote` → 条目被丢 | 否 |
| 规则兜底：引文不在原文丢弃 | 是 | 桩件给库里没有的引文 → 被丢（归一化后子串判据） | 否 |
| 规则兜底：谓词不在受控词表丢弃 | 是 | 桩件给表外谓词 → 被丢 | 否 |
| 重试两次后转人工补录 | 是 | 桩件连续失败 → 计数与「转人工」状态可断言 | 否 |
| 时间归一（`normalize_time`） | 是 | plan 阶段一步骤 4 的参数化用例 | 否 |
| **真实抽取质量**（准确率、条目密度、`≥120 卡片 / ≥400 事实` 的达标判定） | **否（标注为待补 key）** | 需要真实后端跑真语料；本轮只允许记录「桩件通过」，**不得据此宣布达标** | **是** |
| 人工校对 10% 与错误率判定 | 依赖真实抽取 | 桩件不产生真实卡片，无法抽样；记为待补 | 是 |

结论：**阶段一「可验证部分」= 上面 8 行「否（不需要 key）」的项**；plan 阶段一步骤 9 的入库数量指标（卡片 ≥120、事实 ≥400）在拿到 key 之前**只能标未达标原因，不能标通过**。
