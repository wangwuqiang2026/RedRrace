# 决策记录 001 —— 检索引擎选型（阶段零步骤 7）

- **日期**：2026-11-13
- **决定**：**选甲路径（自研轻量管线：bge-m3 本地向量 + BM25 稀疏检索 + FAISS/SQLite）**。
- **首要理由**：**本项目不使用 Docker（用户明确指令）**。乙路径 RAGFlow 官方部署形态依赖 Docker（官方 README/Quickstart：Docker 部署为推荐路径，Docker ≥ 24.0.0、Compose ≥ v2.26.1，镜像仅发布 Linux x86-64 / ARM64），已被排除，**不再展开部署难度对比**。
- **佐证理由（与 Docker 无关，静态取证成立）**：本项目两项核心要求——引文定位到页码/章节/段落的事实条目级、同一「主体+谓词」多来源取值不一致时并列两条来源——RAGFlow 均不内建（详见维度 1、2 的证据），即便允许 Docker 也省不掉自研主体工作量。
- 所有标注「实测」的数字均在本机当次执行取得；「推测/估算」一律不进入验收依据，收敛进文末未决项。

   - 模型卡**未发布 int8 量化权重**，**未提供 CPU 推理耗时数字**。
   - 参考：论文 <https://arxiv.org/pdf/2402.03216>、代码 <https://github.com/FlagOpen/FlagEmbedding>。

## 四、评估维度（与 Docker 无关的四项）

### 维度 1：引用定位精度 —— 自研路径的闭环设计

**要求**：每条结论句绑定的事实条目必须能定位到页码/章节/段落（计划全局约束 2、选题书 7.(2)）。

**甲路径怎么保证**（链路全部在自己代码内，可测试可回归）：

1. **解析即定位**（阶段一步骤 3）：`ingestion/parse.py` 对每类载体写入 `Locator`——PDF 用 pypdf 按页取文带页码；EPUB 按章节+段落；TXT 按空行分段保留标题路径；Word 按段取文带段号；网页用 BeautifulSoup 拼标题路径并保留锚点。解析产物落 `data/parsed/<来源编号>.json`，原文与定位同仓保存。
2. **条目带逐字引文**（阶段一步骤 7）：抽取的每条事实条目必须附**逐字引文**，无引文即丢弃（规则兜底），引文生成时就携带其来源 Locator。
3. **三道校验**（阶段三步骤 4）：编号合法 → **引文在解析原文归一化（全半角/空白/标点）后子串命中**（这就是"定位到段落"的机器判据）→ 主体一致。任何一句校验不过即剔除，全剔则拒答；引文可定位率 ≥98% 是硬指标。
4. **导出与回链**：三视图、路线、素材包的每个点位复用同一出处卡片组件回链原文位置。

**反证（为何现成引擎不解决此项）**：RAGFlow 的定位粒度是 chunk（文档块）级；且对网页/txt 载体 `positions` 为空（官方 API 文档示例原文），与本项目"语料大量为官方文章 HTML 快照"的形态不匹配——即使接入也只能拿到 chunk，页码/标题路径/锚点仍要自己建。**扫描件 OCR 后引文逐字定位率下降是甲路径的真实风险点**，应对与量化见计划阶段零步骤 6 与阶段九演练 4（优先文字版、OCR 抽样不合格不入语料）。

### 维度 2：冲突二次开发成本 —— 自研路径的实现设计

**要求**：同一「主体+谓词」多来源取值不可兼容时，成组、两条来源并列、标注存疑，系统不判定谁对（全局约束 4、杀用例）。

**甲路径实现**（即计划阶段四，本决策确认其为核心工作量、无可外购）：

1. **归一**：`consistency/claims.py` 的 `claim_key(条目) = 主体归一(去空白/别名表/全半角) + 谓词(受控词表：生卒年、籍贯、职务、参与事件、事件时间、事件地点、事件结果、人物关系) + 取值粒度`。时间走 `normalize_time`（解析失败保留原文、粒度标「未知」，绝不猜）；地点人物走 `aliases.yml` 别名表。
2. **成组**：`consistency/detect.py` 按冲突键聚合、取值去重后 >1 即成组；**粒度可兼容不算冲突**（「1949 年」与「1949 年 4 月」取细粒度并留痕），只有不可兼容才成组标注存疑。
3. **留证**：组内每条取值保留各自的条目编号、来源编号、逐字引文与 Locator——"两条来源并列展示"的数据基础。冲突表状态：待处理/已处理/存疑。
4. **钩子与演示**：入库时自动检测 + 支持全量重算；`scripts/killer_inject.py` 注入矛盾记录（独立来源编号通过登记校验）、重建索引、`--restore` 一键还原，支撑杀用例端到端测试与答辩演示。
5. **成本判定**：以上模块全部落在既有计划排期（阶段四，第 4 周）内，验收证据（冲突组两来源并列、杀用例通过）不变——**选甲不增加额外工期；若选乙，这套逻辑依旧要全部自建，还多出 chunk→事实条目的映射层**。

### 维度 3：CPU 可行性 —— 内存可行，耗时未实测

- **参数规模（估算，有实测基础）**：`pytorch_model.bin` 实测 2,165.9 MB ÷ 4 字节/参数（config 为 float32）≈ **5.4 亿参数**，与 XLM-RoBERTa-large 级架构（24 层×1024）相符；标注为**由文件大小推算**，非官方口径。
- **内存判断（结合实测 15.7 GB 本机）**：float32 权重约 2.2 GB；官方推荐 `use_fp16=True`（模型卡原文：提速且性能仅轻微下降）后约 1.1 GB；FAISS 平面索引按 ≤2,000 条事实条目 ×1024 维 float32 ≈ **8 MB**（估算，规模由计划阶段一产出上限 400 条起、留足冗余推算）。**整机内存余量充足，无需显卡，符合硬件档 B 约束。**
- **ONNX/int8**：官方仓库**自带 ONNX 权重**（实测存在，2.16 GB）；**官方未发布 int8 权重**；FlagEmbedding 当前 master 的 M3 封装源码中未检索到内置量化参数（2026-11-13 检索其 `inference/embedder/encoder_only/m3.py` 全文，无 `quant` 命中）——int8 需走 ONNX Runtime 动态量化工具链，属通用能力，精度损失**未实测**（未决项 2）。
- **耗时**：**官方无任何 CPU 耗时数字，本机未实测**（遵守任务纪律，未下载数 GB 模型跑测）。可用的官方定性依据：模型卡明示"更小的 max_length 可加速编码"；1.0 版 RAGFlow 尚能全 CPU 跑 DeepDoc 亦旁证 CPU 小模型可行（旁证，非本项目指标）。量化目标直接采用计划既有线：阶段八冷机验证——**建索引（50–80 单元、≥400 条）≤10 分钟；在线生成 P95 ≤8 秒**，在阶段二用 `scripts/build_index.py` 实测标定（未决项 1）。

### 维度 4：工期影响 —— 甲让阶段二/三/四按期，风险集中在可自测的应用层

- **阶段二（检索层）**：甲路径与计划完全同构（bge-m3 dense + BM25 稀疏 + RRF 融合 + bge-reranker-base 重排 + 阈值标定），零外部服务联调；风险是开发集命中率 ≥85% 要靠调参达成，兜底为融合权重与别名表调整、BM25 单独可用（降级路径 3）。
- **阶段三（可溯源问答）**：引用三层校验依赖阶段一的 Locator 质量——甲路径里"解析、抽取、校验"同一批代码，问题暴露最早、修复半径最小。
- **阶段四（冲突）**：见维度 2，本就是自研；选甲排期不变。
- **依赖清单**：全部在计划阶段零步骤 1 基线内（sentence-transformers、rank_bm25、jieba、faiss、pypdf/ebooklib/python-docx/bs4、SQLite），**不含任何 Docker / docker-compose 项**；若 ONNX Runtime 路线实测更优，按准入五条登记后增补 `optimum`/`onnxruntime`。
- **对照更正**：计划「阶段八步骤 6 提到 `docker-compose.yml`（可选）」——实测原文位于 **plan.md 阶段八「涉及文件」清单**（约 744 行：新建 `RUNBOOK.md`、`.env.example`、`docker-compose.yml`（可选）），非步骤 6 正文。**因本项目不使用 Docker，该可选项自本记录起取消**；阶段八步骤 6 运行手册以"pip 安装 + uvicorn/pnpm 直启"为唯一路径（原文已如此，无需改动）。plan.md 保持只读，不改。

## 五、降级触发

1. **语料不足**：第 10 个自然日来源单元 <50 → 切**最小可交付集：电子书 5 部 + 官方文章 45 篇**，卡片/条目验收口径按实际语料量在评测报告如实说明（计划阶段零步骤 6 既定线，不因此停摆）。
2. **解析瓶颈**：阶段一扫描件占比高、pypdf/ebooklib 路线一周内达不到引文逐字定位要求 → 在甲路径内更换解析器（MinerU、unstructured、PaddleOCR 等，计划可替换点，均不依赖 Docker），产物仍走自建 Locator 与条目抽取。
3. **召回瓶颈**：阶段二命中率连续两轮 <85% 且调参无效 → 先换向量模型（bge-large-zh/m3e/gte 等可替换点）与调融合参数，仍不达标则把根因写入评测报告并降指标口径答辩，不引 Docker 类外部引擎。
4. **（远期）** 若用户将来允许 Docker 且出现必须整体换引擎的场景，按第一节：实现 `RetrievalBackend` 适配器接入现成引擎，上层不动。

## 六、回滚与可替换约定（换引擎不动上层）

- **唯一契约**：`retrieval/backend.py` 的 `search(问题, 条数) -> list[Hit]`；`Hit` = 条目编号、卡片编号、综合分、稠密分、稀疏分、重排分（计划阶段二接口约定原文）。上层 `qa/pipeline.py`、`qa/refusal.py`、阈值标定、全部 API/前端只消费 `Hit` 与出处结构。
- **开关**：`Config` 保留检索引擎选择项（`.env.example` 登记；本决策下生效值为 `local`）。
- **回滚动作**：更换向量模型/索引/稀疏检索时，只替换 `retrieval/local.py` 内部实现与 `scripts/build_index.py`；索引带语料指纹，语料变更即重建；删除新依赖、恢复 `.env` 即回基线（准入条件 5）。
- **契约保护**：五条输出契约（接口路径与字段、必带出处、冲突并列、明确拒答、禁止创造性补充）不随任何替换变化；阶段九评测用替换后系统重跑全部指标，达标线不放宽。
