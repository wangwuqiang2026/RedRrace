## 阶段二 · 检索层（2026-11-17/18 实测）

### 语料与索引规模（试点口径）

| 项 | 实测 |
|---|---|
| 来源单元 | 20 纳入 / 11 可解析（9 部核心电子书本地无原件，见「已知限制」） |
| 卡片 | 125 张（event 88 / person 22 / place 9 / relation 5 / time 1） |
| 事实条目 | 223 条 |
| 检索块（single 切块） | 223 块，倒排词条 1035 |
| 检索块（merged 切块） | 125 块（按卡片合并） |
| 向量 | 223 × 1024 维（`qwen3.7-text-embedding-flash`） |
| 建索引耗时 | single 11.8 s / merged 6.3 s |

**首要限制：这不是全量语料。** 登记表 180 行里有 9 部核心电子书（S002/S003/S006–S012，含
《中国共产党历史》《图说长征》等）本地无原件，因此试点只覆盖 20 个单元。规划中的「卡片 ≥120 /
条目 ≥400 / 单元 ≥50」三条退出线，**卡片已达标（125），条目（223/400）与单元（11/50）未达标**。
按用户 2026-11-16 授权，本轮只跑试点范围，正式全量数字待补采原件后重跑。

### 三指标（开发集 100 题：50 可答 + 50 不可答）

可答题取自已入库卡片并绑定期望条目与关键事实；不可答题为库外真实红色史实实体（先核该实体
未出现在任何已入库条目中，3 个冲突项已剔除并补足）。

| 口径 | 题数 | Hit@1 | Hit@3 | Hit@8 | MRR | 关键事实覆盖率 |
|---|---|---|---|---|---|---|
| **全量库（223 条，稠密+稀疏融合）** | 50 | **0.64** | **0.86** | **1.00** | **0.7787** | **1.00** |
| 迷你库（仅相关单元，稀疏口径） | 50 | 0.68 | 0.98 | 1.00 | 0.815 | 1.00 |

- 达标线（plan 步骤 6）是「前 8 条含正确条目的命中率 ≥85%」→ **Hit@8 = 1.00，达标**。
- **摊薄效应确实存在**：同一批题在「只放相关单元」的迷你库上 Hit@3 为 0.98，在全量库上掉到
  0.86、MRR 掉 0.036 —— 检索排得到，但名额被无关块分走了（plan 6c 预警的形态）。Hit@8 未受影响。
- **迷你库口径只走稀疏通道**（诚实标注）：向量通道没有「按单元范围下推」的接口，这一行只作摊薄
  趋势参考，不是严格同条件对照。

复现：`cd backend && python scripts/eval_retrieval.py --minimal`

### 两项扫档实验（plan 3c 与 T5 第 5 项）

| 实验 | 结果 | 结论 |
|---|---|---|
| `retrieval_rrf_constant` = 20 vs 60 | **五个指标完全相同**（0.64 / 0.86 / 1.00 / 0.7787 / 1.00） | **无收益**，如实记录。定稿保持 60（计划基线），依据：融合后的排序实际由稠密分与稳定序主导，稀疏只做补位，常数在这个量级上改不动名次 |
| `block_mode` = single vs merged | single 0.64 / 0.86 / 1.00 / 0.7787；merged **0.64 / 0.68 / 0.68 / 0.6567** | **合并档明显更差**（Hit@8 从 1.00 掉到 0.68）。原因：合并块把同卡片的多条事实塞进一个检索串，期望条目与同卡片其它条目共用一个块，命中粒度变粗；且 merged 只有 125 块，`k=8` 时证据集覆盖的信息量下降。**定稿 single** |

复现：
```
cd backend && python scripts/eval_retrieval.py --rrf 20
cd backend && python scripts/build_index.py --out data/index-merged --block-mode merged --rebuild
cd backend && python scripts/eval_retrieval.py --out data/index-merged --block-mode merged
```

### 拒答阈值标定（plan 步骤 5 / 6 / 6b-2）

扫描带 **0.40 → 0.60**（不采用参考实现的 0.45，见禁止清单 8.12）。选点规则：可答误拒保持 0%
的一侧取不可答拒答率最高。

| tau | 不可答题正确拒答率 | 可答题误拒率 |
|---|---|---|
| 0.40 | 8%（4/50） | 0%（0/50） |
| 0.45 | 40%（20/50） | 2%（1/50） |
| 0.50 | 74%（37/50） | 6%（3/50） |
| 0.55 | 90%（45/50） | 8%（4/50） |
| 0.60 | 98%（49/50） | 22%（11/50） |

- **定稿 tau = 0.41**（误拒 0% 一侧的最高拒答率点），写入 `backend/data/index/threshold.json`，
  文件自带标定条件（语料指纹 `0693bb14…`、向量配置签名 `dee27563…`、稠密/稀疏 top 30/30、
  融合常数 60、block_mode single、top_k 8、生成时间）与完整曲线。
- **可分性：重叠** —— 可答题最低分低于不可答题最高分，**任何单一阈值都无法把两类完全分开**。
  这不是实现缺陷，是试点语料 + 稠密相似度的真实区分度：task0 报告 6.4-1 已预警「条目级检索串
  平均 24.6 字符，语义信息量薄，预期稀疏一路强于稠密一路」。
- **达标判定**：plan 5.19 要求不放宽断言。此处如实标注：**「阈值能把两类分开」这一条在试点语料
  上未达标**。补采核心电子书、把条目量拉到 400+ 后重跑，是唯一合规的改善路径（调低扫描带或
  改选点规则都属放宽口径，不做）。

复现：`cd backend && python scripts/eval_retrieval.py --calibrate`

### 已知限制（照写不回避）

1. **语料不完整**：9 部核心电子书缺原件，试点 20 单元 / 223 条目远低于计划的全量规模；单元数
   是比卡片数更硬的瓶颈（单产率折算：约 24 单元才够 400 条目）。
2. **阈值可分性未达标**：见上节。
3. **置信度无区分度**：223 条 `confidence` 全部落在 [0.9, 1.0]，不能作为拒答阈值的输入。
4. **时间字段稀疏**：仅 23/223 条有 `time_start`，`granularity` 以 unknown 为主 —— 时序检索
   在此数据集上**没有验证过**，阶段五的时间轴只做展示不做过滤。
5. **`page` 恒为 None**：试点语料全是 HTML 文章，PDF/EPUB 的页码定位分支只用 fixture 覆盖，
   **不是**「真实语料已验证」。
6. **无跨来源同名卡片**：`(type, name)` 分组无重复组，阶段四的冲突检测**不能用这批数据验收**。
7. ~~**重排未生效（外部原因）**：`qwen3-rerank` 端点返回 `HTTP 400 Arrearage`（账户欠费），本轮
   真实重排无法验证；已用 `local_lexical` 档跑通全链路并验证「尺子隔离」（重排前后
   `max(Hit.score)` 完全一致）。账户恢复后需重跑一次 API 档冒烟。~~ **已关闭（2026-11-19）**：
   账户充值后重跑真实 API 冒烟，结果见下节「真实 API 重排冒烟（2026-11-19）」。
8. **稠密相似度的绝对水平偏低**：真实索引上「省立第一师范学校讲习所 何时创设」的第一名是
   无关条目（cos 0.383）。`Hit.score` 在无关语料上能到 0.38，是阈值下界必须实测而非拍数字的
   直接证据。
9. **重排账户欠费导致 API 档未实测**（同第 7 条），阶段八真实重排延迟/分数分布仍属未决项。

> **2026-11-19 修订说明（评审修复）**：`embedding.py` 修复了四项「断言全过但产出不可用」的缺口——
> ① token 估算把中文标点/全角/假名按 4:1 低估（引文混排串的主形态，客户端放行后服务端整批 400）；
> ② NaN/Inf 分量穿透五项断言使余弦比较恒 False；③ 注入 loader 绕过可选依赖检查；④ 空输入列表
> 返回 `dense_available=True` 的空成功。以上在校准与评测数字产出后修复，均为防御性加固，不改变
> 索引/向量/阈值产物，故上表实测数字无需重跑；可复现性判据按 R18 定为 cos ≥ 0.998。全量回归

### 真实 API 重排冒烟（2026-11-19，账户充值后补跑）

原「账户欠费」限制已解除。补跑时先暴露并修复了一处**欠费期间被掩盖的形态缺陷**：`ApiReranker`
原发嵌套 `{"input": {"query":..., "documents":[...]}}`（DashScope 原生端点形态），兼容端点
`compatible-api/v1/reranks` 回 `HTTP 400 InvalidParameter: Field required: input.query & input.documents`；
改为扁平 `{"model":..., "query":..., "documents":[...]}` 后成功（已补 RED→GREEN 测试
`test_api_reranker_sends_flat_query_and_documents_body`）。取证见
[阿里云百炼重排序文档](https://help.aliyun.com/zh/model-studio/rerank#1)（OpenAI 兼容 `client.post("/reranks", body={...})` 示例为扁平字段）。

| 项 | 实测 |
|---|---|
| 模型 / 端点 | `qwen3-rerank` / `compatible-api/v1/reranks` |
| 请求 | 1 query + 5 文档（扁平 `query` / `documents`） |
| 返回 | 5 条 / 5 条（条数相等），分数 0.2448–0.8371 |
| 耗时 | 0.81–0.88 s（5 文档） |
| 尺子隔离 | 重排前后逐 hit 的 `Hit.score` 按 claim_id 对齐**完全一致**；`max(Hit.score)` 均为 0.8；只有顺序变化（相关文档从第 2 抬到第 1） |
| 回退纪律 | 失败仍走 `logger.warning("重排未生效: ...")` + 按融合序返回（既有测试覆盖） |

分数分布落在 007 第二节记录的 0.2–0.85 平缓区间，与该模型的定性结论一致。复现命令（探针为临时文件，
用后即删）：`cd backend && python -c "from app.retrieval.rerank import ApiReranker; from app.core.config import get_config; print(ApiReranker(get_config()).rerank('when was the school founded', ['doc1','doc2']))"`。

## 阶段三 · 可溯源问答（2026-11-19 实测）

### 真实 LLM 端到端冒烟（真索引 + 真在线模型 + 三层校验）

用试点库 223 条目建的真索引、`qwen` 在线生成模型、τ=0.41，逐条问答（探针为临时文件，用后即删）：

| 问题 | 检索最高分 | 结果 | 说明 |
|---|---|---|---|
| 省立第一师范学校讲习所何时创设？ | 0.3707 | `not_covered` 拒答 | 分数低于 τ=0.41——阶段二「可分性重叠」的已知局限，非流水线缺陷 |
| 红军长征何时开始？ | 0.7063 | **回答 + 1 条已验证出处** | 答案「自1934年10月起，各路红军被迫相继开启战略大转移[1]。」，三层校验通过 |
| 遵义会议什么时候召开？ | 0.6013 | `all_claims_rejected` 拒答 | 真模型该次草稿未通过逐字定位，闸门按「宁可拒答不编造」处理 |

**关键修复（冒烟暴露，已 TDD 回归）**：① 逐字定位的原文必须读 parsed 的 `full_text`（blocks 拼接会
切断引文）；② `source_texts` 的键必须是 **claim_id** 而非引用序号 `[n]`（真实 claim_id 是三位数，
用引用号查会全查不到，导致所有真模型答案被误判 `quote_not_found` → 永远拒答）；③ 旧库写日志前
幂等跑 V2 迁移。修复后中间那条问题成功返回带出处的答案——完整链路（真检索→真 LLM→三层校验→
出处回链）在真实数据上跑通。
